# 从现象定位问题

## 先建立一个正常结果

本课使用 Learning07_Blink。下载顶部工程包，构建并运行：PB12 经 330 Ω 电阻驱动绿灯，每 500 ms 翻转一次，完整亮灭周期约 1 s。先保留这份正常工程，再逐项制造故障；每次只改一个地方。

排错记录至少写清四件事：改了什么、预期什么、实际什么、证据在哪里。一个“灯不亮”可能来自代码、引脚配置、极性或接线，不能只凭画面判断。

## 区分问题发生在哪一层

| 阶段 | 常见现象 | 第一项检查 |
| --- | --- | --- |
| 导入 | 没有 main.c，找不到头文件 | 是否选了含 IOC、Core、Drivers 的工程根目录 |
| C 编译 | 类型未声明、缺少分号、参数不匹配 | 日志中的第一条错误及其前一行 |
| 实机链接 | undefined reference、重复符号 | 函数实现是否参与构建，定义是否重复 |
| HAL 建模 | 明确指出不支持的调用或表达式 | 函数名、源码位置、软件版本及最小复现 |
| 固件运行 | Error_Handler、超时或运行停止 | 初始化返回值、外设配置、停止时的日志 |
| 逻辑与接线 | 程序运行但输出不符合预期 | 分支输入、GPIO 网络、LED 极性与供电 |

AliceSIM 的 HAL 构建并不是生成 ARM 可执行文件的实机链接流程。语法检查通过之后，还要等 HAL 建模和电路绑定完成；“包络预览正常”也不能代替固件运行成功。

## 实验一：看懂第一条编译错误

在 PB12 的一次 `HAL_GPIO_TogglePin` 调用末尾临时删掉分号，重新构建。编译器可能把错误位置指到下一行，因为它在那里才发现语句没有结束。回到前一行补回分号，再构建，确认错误消失。

遇到十几条报错，先修最前面的那条，再重新构建。一个缺失声明可能带出许多后续错误，不要同时修改十处。

## 实验二：把代码输出与灯分开核对

暂停仿真并断开 LED 回路中的一根导线，再构建运行。用逻辑分析仪观察 PB12：如果它仍在高低翻转，说明程序已经写到了输出，下一步应检查电路。停止仿真，恢复导线后再次运行。

再做一次代码故障：只把循环中的输出脚从 PB12 改成 PB13，保留 PB12 的初始化与电路。构建可能仍能通过，但原来的灯不会按预期闪烁。比较宏定义、`MX_GPIO_Init()` 与电路三个位置，恢复为同一个引脚。

这类实验只在副本里进行。正常工程中不要把未初始化的 GPIO 当作第二个可用输出。

## 实验三：区分半周期与完整周期

把 `HAL_Delay(500U)` 改成 `HAL_Delay(200U)`。预期每次翻转间隔约 200 ms，一个亮灭周期约 400 ms。先在纸上写下预期，再对照波形时间轴，不能把两者混为一谈。

如果你想让灯每秒闪一次，`HAL_Delay(1000U)` 加一次翻转得到的通常是约 2 s 的完整周期。实际循环还包含函数调用时间，阻塞延时不能提供严格的周期调度。继续阅读 [非阻塞计时与状态机](tick-state.md) 和 [定时器基础与更新中断](timer-irq.md)。

## 保留有用的运行信息

展开电路页的构建与运行日志，保留第一次失败的信息。使用串口排查复杂例程时，记录输入、状态和计算结果；只在变化时或按固定间隔输出，避免每次循环都打印。中断回调里先记录标志，主循环再发送文字。

若停止在 `Error_Handler()`，应追到调用它的返回值检查：是哪一次时钟或外设初始化失败，参数是否与芯片一致。删除 `SystemClock_Config()` 或错误分支可能让现象消失，却会改变定时器、串口和系统时基的条件。

## 自己完成一次排错

请同学在工程副本中任选一种故障：错误引脚、断线、反接 LED、错误周期或缺少头文件。另一人只看现象和日志来定位，并提交修复前后的证据。最后保存完整项目、重新打开并运行，确认修复没有只停留在旧构建结果里。

下一课 [把程序放到真实开发板](hardware.md) 介绍下载、断点与单步；这些操作由实机调试工具完成。
